# PAY-9 — Direct Terminal / SoftPOS Boundary

Status: PROVIDER-NEUTRAL SOFTWARE BOUNDARY IMPLEMENTED / PROVIDER EXECUTION BLOCKED

## What is implemented

Balcona now has a provider-neutral terminal domain:
- branch-scoped terminal/device records;
- provider and test/live environment;
- provider terminal/device/merchant references;
- runtime secret references only;
- readiness and live-verification fields;
- terminal payment request lifecycle states;
- idempotency keys;
- bill/branch/company/staff binding;
- audit evidence;
- explicit blocked request records;
- Office Money readiness UI;
- Setup readiness gate;
- Service Bills distinction between direct terminal execution and manual external POS tender.

## Critical product distinction

`card_pos` is a **manual record of an external terminal payment**.

It is not:
- a server-to-terminal command;
- a SoftPOS SDK invocation;
- a provider callback;
- a device approval signal generated by Balcona.

Service copy explicitly instructs staff to record `card_pos` only after the separate terminal approves the transaction.

## Why direct execution remains blocked

Current public provider material proves that in-person payment products exist, but does not establish the exact merchant contract Balcona needs to safely control a terminal.

Before a provider adapter can send a money request, Balcona requires:
1. device/terminal provisioning contract;
2. branch/merchant/terminal binding;
3. authenticated server-to-terminal request;
4. exact amount/currency semantics;
5. provider request and transaction references;
6. approval/decline/cancel/timeout/unknown states;
7. callback authenticity or authoritative inquiry;
8. duplicate/retry rules;
9. refunds/reversals if supported;
10. test terminal or SoftPOS test environment;
11. settlement/reconciliation reference mapping.

## Fail-closed behavior

If staff tries to start a direct terminal request before provider execution is verified:
- Balcona records a `blocked` request;
- no provider request is sent;
- the bill is not settled;
- no manual payment is fabricated;
- the blocker is auditable.

An unresolved online payment also blocks terminal collection to reduce double-payment risk.

## Live certification

Direct terminal payment becomes live-verified only after a controlled real/test-device flow demonstrates:
request -> device -> approval/decline -> authenticated Balcona truth -> exactly-once bill settlement -> reconciliation.

Until then: **PAY-9 PROVIDER EXECUTION BLOCKED**.
