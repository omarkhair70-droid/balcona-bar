# Balcona Visual Benchmark System

Status: LOCKED FOR PROTOTYPING
Date: 2026-08-28
Branch: `ux/product-ia-overhaul`

## Principle

Balcona must not imitate a single hospitality platform.

The method is the same evidence-led method used for the portfolio:

**Reference principles × Balcona product truth × Balcona identity = final system**

A benchmark is included only when it contributes a specific strength.

## Global formula

**Balcona = Lightspeed structure × Toast operational insight × Square interaction clarity × Oracle scope discipline × me&u guest product thinking × Balcona warm hospitality identity**

This is not a visual average. Each reference owns a different problem.

---

# 1. Balcona Office benchmark stack

## Primary reference — Lightspeed Restaurant Back Office

Use for:
- business-domain navigation
- dense management information
- page hierarchy
- tables/filters
- separation of Back Office from live POS
- reduced menu depth
- functional rather than decorative chrome

Why:
Lightspeed explicitly reorganized its Back Office navigation around how features relate to the business and reduced menu depth after product growth.

Do not copy:
- brand colors
- exact labels
- exact sidebar layout
- product-specific modules Balcona does not have

## Secondary reference — Toast Web

Use for:
- management Home/reporting overview
- high-level KPI → drill-down relationship
- owner/manager decision hierarchy
- multi-location location context
- permissions-aware reporting
- operational support/device health ideas

Why:
Toast keeps high-level dashboards small enough to scan, while deeper investigation happens in reports.

Do not copy:
- Toast orange/black identity
- Toast-specific labor/payroll modules
- hardware-first product assumptions

## Interaction reference — Square Dashboard / Restaurants

Use for:
- clarity of states
- touch/action discipline
- device/mode thinking
- floor/table operational state
- settings ergonomics
- close-of-day/checklist interaction

Do not copy:
- generic Square ecosystem styling
- blue/white visual system
- consumer-payment patterns that do not fit hospitality management

## Architecture-only reference — Oracle Simphony

Use for:
- enterprise → location hierarchy
- inherited/default/override semantics
- scope-aware configuration
- enterprise administration discipline

Do not copy:
- visual styling
- dense legacy desktop grammar
- terminology such as Property/Revenue Center unless Balcona needs it
- enterprise complexity for single-location tenants

## Balcona contribution

Keep:
- warm hospitality personality
- bronze/copper family
- deep warm brown/burgundy brand memory
- bilingual Arabic/English identity
- existing detail-panel interaction where it works

Change:
- dark glass as universal default
- glow-heavy primary actions
- giant presentation headers
- repeated card dashboards

## Office formula

**Lightspeed information architecture + Toast decision hierarchy + Square clarity + Oracle scope + Balcona warmth**

Target feeling:

> Hospitality company control room — calm, dense, trustworthy, not generic enterprise software.

# 9. Shared visual rules

## Typography
- modern grotesk/sans primary
- numeric/data hierarchy must be excellent
- Arabic and English must both feel native
- avoid giant marketing-scale page titles in Office

## Grid
Office:
- broad desktop canvas
- strong table/list alignment
- 12-column mental model where useful
- side detail panels

Guest:
- mobile flow

Service:
- split operational panes

Kitchen:
- ticket grid

## Containers
Use containers only when they communicate grouping.

Avoid:
- card around every heading
- card around every KPI
- nested cards for routine data

## Corners
- modest, consistent
- softer in Guest
- flatter in Office/Kitchen

## Elevation
- overlay/detail/dialog only
- not default content styling

## Color
Color communicates:
- brand accent
- state
- attention

Never use decorative color where status already uses color.

# 11. Non-copy rules

Do not:
- duplicate any competitor's exact layout
- copy visual identity
- use modules Balcona does not support
- add Reservations/Labor/CRM because a reference has them
- create fake KPIs for visual balance
- add generic "business health scores"
- create charts without a real supported metric
- add shortcuts just to fill whitespace
- call a design successful because it looks like a polished SaaS template

Every visible element in a final Balcona prototype must answer:

1. Which Balcona job does this serve?
2. Which backend/product truth supports it?
3. Which benchmark principle informed it?
4. Why is it prominent at this frequency?

If those cannot be answered, remove it.

---

# 12. Prototype gate

No image generation or production implementation is approved from a generic prompt.

Before each flagship prototype:
1. choose its reference stack
2. define exact Balcona data/jobs
3. define layout grammar
4. define what is intentionally absent
5. define populated + exception + empty states
6. define Arabic/RTL treatment
7. only then prototype in code/design tooling

This document is the visual benchmark source of truth for the overhaul.
